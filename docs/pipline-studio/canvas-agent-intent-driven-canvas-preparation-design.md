# Pipeline Studio Canvas Agent 意图驱动的画布准备设计

> 状态：当前开发设计基线  
> 日期：2026-09-07  
> 范围：用户意图理解、创作规划、节点自动创建与配置、Route 选择、提示词、素材引用、布局和手动生成边界  
> 关联文档：[Canvas Agent 意图驱动的生成编排设计](./canvas-agent-intent-driven-production-orchestration-design.md)、[Canvas Agent 产品调研与技术方案](./canvas-agent-product-research-and-technical-design.md)、[Canvas Agent 开发计划](./canvas-agent-development-plan.md)

## 1. 设计结论

当前阶段的 Canvas Agent 应聚焦一个简单、可验证的核心能力：

> 用户用自然语言说明想完成的内容；Agent 理解本轮意图，在用户要求的范围内完成创作规划，并把画布节点、模型 Route、参数、提示词、素材引用、连线和布局全部准备好；所有内容生成都由用户在节点或工作流上手动触发。

Agent 负责减少用户的创作规划和技术配置负担。用户负责确认创作方向，并决定何时产生实际生成费用。

本设计取代上一版设计中当前阶段的自动生成、Route 评分、生产计划、自动重试预算和质量闭环方案。上一版文档保留为长期能力参考，不作为近期实现要求。

## 2. 为什么这样收敛

当前最明显的用户负担发生在生成之前：

- 不知道应该创建哪些节点；
- 不知道剧本怎样拆成可生成的镜头；
- 不知道不同镜头应该使用哪类模型；
- 不知道提示词应该怎样适配模型；
- 不知道参考图片、视频和音频应该连接到哪里；
- 不知道 Route 参数如何设置；
- 不知道节点之间的依赖是否正确；
- 创建大量节点后还要手动整理画布。

只要 Agent 能把画布准备成可靠的可运行状态，已经可以消除大部分重复劳动。让用户手动触发生成还能提供清楚的费用边界，并让产品先验证 Agent 的规划和配置质量。

## 3. 产品边界

### 3.1 Agent 可以做什么

Agent 可以：

- 与用户多轮讨论创意；
- 编写和修改 brief、剧本、旁白、对白和分镜；
- 分析画布上的图片、视频、音频和文本；
- 根据用户意图决定需要创建或修改哪些节点；
- 自动选择当前项目已启用且输入条件匹配的 Route；
- 自动填写节点提示词和 Route 参数；
- 自动绑定已有素材，建立合法引用边；
- 自动创建必要的中间节点；
- 自动命名、分组和排列节点，避免重叠和遮挡；
- 检查节点是否达到可生成状态；
- 分析已有生成结果并修改相关节点配置；
- 将一组画布修改作为一个可撤销 Action 应用。

### 3.2 Agent 不做什么

当前阶段 Agent 不直接：

- 调用图片、视频或音频生成接口；
- 启动 Workflow Run；
- 自动重试生成；
- 因为结果不满意而产生新的付费任务；
- 在用户只要求讨论或写作时擅自搭建完整生成流程；
- 要求用户逐项确认模型参数、素材槽位和提示词格式。

用户在节点或工作流上点击生成后，继续使用现有 Generation Run、Provider Job 和 Workflow Run 链路。Agent 与手动生成共享同一份节点配置，不建立隐藏的执行配置。

### 3.3 “帮我生成”如何处理

即使用户在聊天中说“帮我生成这段视频”，当前阶段也按以下方式执行：

1. Agent 把目标理解为“准备可生成的视频流程”；
2. 创建或更新所需节点；
3. 完成 Route、参数、提示词、引用和连接；
4. 进行配置检查；
5. 明确告诉用户哪些节点已经可以生成；
6. 用户点击节点或工作流的生成按钮后，才真正提交任务。

聊天中的自然语言请求不能直接产生费用。这样无需再让用户理解“允许 Agent 自动生成”开关与本轮意图之间的复杂关系。

## 4. 用户意图与停止位置

Agent 每轮首先判断用户需要什么交付，而不是默认执行完整短剧流程。

| 用户意图 | 本轮行为 | 停止位置 |
| --- | --- | --- |
| 讨论创意 | 回答、分析、提出少量必要问题 | 不修改画布 |
| 编写剧本 | 生成或修改文本内容 | 剧本文本完成 |
| 设计分镜 | 生成镜头清单和镜头设计 | 分镜内容完成 |
| 搭建画布 | 创建并完整配置相关节点 | 节点可生成 |
| 调整节点 | 修改指定节点及必要的直接关联 | 配置更新完成 |
| 分析素材 | 输出分析；用户同时要求使用时才绑定节点 | 分析或绑定完成 |
| 分析结果 | 评审现有产物并修改用户要求的节点 | 新配置待生成 |

例如：

- “只写一个剧本”不能创建图片和视频节点；
- “把剧本拆成分镜”不能继续创建视频生成流程；
- “把第 3 镜准备好”只能修改第 3 镜和它确实需要的引用节点；
- “把整部短剧搭到画布”才允许创建完整画布结构；
- “人物衣服换成黑色”应修改受影响的人物与镜头节点，不应重做无关场景。

Agent 可以在完成后建议下一步，但必须等待用户的新请求。

## 5. 简化的回合意图

当前 `CanvasAgentTurnIntent` 的阶段模型可以继续使用，不需要立即引入复杂的动作集合。只增加明确的目标范围和交付描述：

```ts
interface CanvasAgentTurnIntent {
  type: "resolved" | "clarification";
  objective: string;
  requestedStage:
    | "discuss"
    | "script"
    | "storyboard"
    | "canvas"
    | "review";
  effectiveStage:
    | "discuss"
    | "script"
    | "storyboard"
    | "canvas"
    | "review";
  scope: {
    projectWide: boolean;
    nodeIds: string[];
  };
  deliverable: string;
  confidence: "high" | "medium" | "low";
  question?: string;
}
```

说明：

- `generate` 不再是 Agent 回合阶段；生成属于用户在画布上的独立操作。
- 第一版只约束项目和节点范围，不额外引入 shot、entity 等持久标识。
- 新创建的节点通过 Canvas Plan 的临时 ID 表达，并必须与本轮交付直接相关。
- 只有不同理解会显著改变交付时才进入 `clarification`。
- 意图由语义模型根据当前消息、最近对话、选区、`@` 引用和当前画布判断，不使用自然语言正则决定用户含义。

服务端继续根据 `effectiveStage` 限制工具能力，并增加节点范围校验。模型提示词只能指导行为，最终范围必须由 application 层校验。

## 6. Agent 如何自动完成画布准备

一次画布准备回合使用现有 Canvas Plan 完成：

```text
用户请求
  → 语义意图与节点范围
  → 读取相关画布和素材
  → Agent 生成 Canvas Plan
  → 服务端补全并校验节点配置
  → 原子应用节点、引用边和布局
  → 返回“已准备 / 仍缺少什么”
  → 用户手动点击生成
```

### 6.1 一个节点必须准备哪些内容

Agent 创建或修改生成节点时，必须一次写入：

- 节点类型和清楚的名称；
- 适合当前目标的 `routeId`；
- 完整的 `promptDocument`；
- Route Schema 中需要的 `settings`；
- 对应的 `textList`、`imageList`、`videoList` 和 `audioList`；
- 多素材输入的稳定顺序；
- 引用边的角色和顺序；
- 节点所在分组和合理位置；
- 空闲的任务状态，不创建 Generation Run。

节点配置完成后应通过与手动生成共享规则的静态配置检查。上游节点尚未生成时，下游节点可以处于“配置完整、等待依赖”状态；这不属于配置错误。用户不需要再逐项检查才能发现缺少首帧、Route 不支持素材或参数值非法。

### 6.2 Canvas Plan 继续作为唯一写入协议

不新增 `CanvasProductionPlan`。Agent 继续提交现有语义 `CanvasAgentPlanOperation`：

- `node.create`；
- `node.update`；
- `edge.create`；
- `edge.delete`；
- `group.create` 或现有等价分组操作；
- 布局相关语义操作。

Plan Service 负责：

- 解析临时节点 ID；
- 校验节点属于当前项目和本轮范围；
- 校验 Route 已启用；
- 校验参数满足 Route Schema；
- 校验引用素材数量、类型、角色和顺序；
- 校验连接规则；
- 计算不重叠的布局；
- 将整个计划原子转换为 `CanvasMutationBatch`；
- 保存反向 mutation 供用户撤销。

## 7. 实用的 Route 选择方式

当前阶段不建立模型排行榜、加权评分、历史学习或动态质量预测。Agent 直接读取当前项目可用 Route 的真实信息：

- capability；
- description 和 tags；
- input schema；
- 可接受的图片、视频和音频数量；
- 时长、画幅、分辨率和其他参数；
- 是否启用及默认 Route。

Agent 根据镜头目标与现有素材选择 Route，服务端只做确定性兼容校验。

### 7.1 选择规则

使用以下简单优先级：

1. 用户明确指定 Route，且它与节点和素材兼容时使用该 Route；
2. 用户未指定时，选择输入能力最贴合当前素材和目标的已启用 Route；
3. 多个 Route 都适合时，优先使用对应 capability 的项目默认 Route；
4. 没有默认 Route 时，Agent 根据 Route 描述和标签选择一个，并说明在节点配置中；
5. 没有兼容 Route 时停止创建错误配置，告诉用户缺少哪类可用 API。

### 7.2 场景到 capability 的基本映射

| 场景 | 优先 capability |
| --- | --- |
| 只有文字描述生成图片 | `text-to-image` |
| 使用一张或多张参考图生成/编辑图片 | `image-to-image` |
| 没有参考素材生成视频 | `text-to-video` |
| 让一张确定画面动起来 | `image-to-video` |
| 同时参考人物、服装、场景、道具、动作视频或音频 | `multimodal-to-video` 或 `reference-to-video` |
| 明确要求画面 A 精确过渡到画面 B | 支持首尾帧的 `image-to-video` |
| 已有视频与配音需要口型同步 | `lip-sync` |
| 从视频提取人声、背景声或完整音轨 | 对应的 `video-to-audio` Route |

首尾帧不是短剧默认方案。只有用户目标确实要求控制起点和终点时才使用。多个角色、服装、场景和动作参考通常应优先使用能够接受这些素材的参考生视频或多模态视频 Route。

### 7.3 后续新增 API

新增 API 时，只要它按现有受信 Catalog 提供 Route 描述、capability 和 input schema，就能自动进入 Agent 的可选范围。无需为每个模型重新修改评分公式。

Catalog 文案应准确描述适用场景和主要限制。Agent 负责在候选 Route 中做语义选择；服务端负责阻止不兼容配置。真实使用发现某个模型不适合某类场景时，再调整该 Route 的描述、标签或项目默认值，不提前建设复杂推荐系统。

## 8. 提示词与参数

### 8.1 提示词由 Agent 直接生成

当前阶段不新增独立 `ShotProductionSpec` 和 Prompt Compiler。Agent 根据剧本、分镜、连续性信息、素材分析和 Route 描述，直接生成最终 `CanvasPromptDocument`。

提示词至少覆盖与当前节点相关的：

- 主体与身份特征；
- 场景和时间；
- 动作、表演和情绪；
- 景别、机位、构图和运镜；
- 光线、色彩和风格；
- 必要的连续性要求；
- 对白、环境声或音乐要求；
- 对引用素材的准确指代。

Agent 必须避免：

- 在同一提示词中写互相冲突的动作或运镜；
- 把无关的项目设定复制进每个节点；
- 提示词中的“图片 1 / 视频 1”与真实引用顺序不一致；
- 为不支持的 Route 编写无效控制语句；
- 把用户没有要求的剧情继续扩写到后续镜头。

### 8.2 参数由 Agent 填写、服务端校验

参数来源按以下顺序处理：

```text
用户明确要求
→ 当前任务和素材推导
→ Route 默认值
```

Agent 可以设置时长、画幅、分辨率、是否生成声音等字段，但只能使用 Route Schema 声明的参数和值。Plan Service 对参数进行校验；缺省字段使用 Route 默认值；非法值拒绝应用并返回具体原因，让 Agent 在同一回合修正计划。

不增加 `qualityTier`、`costTier`、权重或自动估价模型。用户需要限制分辨率、时长或费用时，通过自然语言明确要求即可。

## 9. 素材分析和引用

Agent 读取素材分析结果后，直接决定素材如何用于当前节点：

- 人物参考用于保持身份和外观；
- 服装图用于保持造型；
- 场景图用于环境与构图；
- 道具或产品图用于保持关键物体；
- 视频用于参考动作、表演或运镜；
- 音频用于对白、节奏、声音或口型；
- 只有明确转场目标时才设置首帧和尾帧。

当前无需扩展新的持久化素材语义枚举。Agent 可以通过节点名称、素材分析内容、提示词资源引用和现有边角色表达用途。等真实场景证明现有结构无法可靠区分用途时，再增加领域字段。

服务端仍必须保证：

- 首帧和尾帧来自图片节点；
- 尾帧不能在没有首帧时单独连接到不支持该模式的 Route；
- 引用数量不超过 Route 限制；
- 素材类型与槽位一致；
- 多模态引用顺序和提示词编号一致；
- 本地素材在用户触发生成后，由 Provider Adapter 负责上传或准备。

Agent 配置节点时不提前上传素材，也不直接保存供应商临时 URL。

## 10. 自动布局

Agent 创建节点时不能提供随意坐标。布局由 Plan Service 根据现有画布边界和新子图拓扑计算：

- 新子图优先放在当前选区右侧；没有选区时放在现有内容右侧；
- 同一流程按依赖方向从左到右排列；
- 同一镜头的文本、图片、视频和音频节点保持清楚的局部分组；
- 节点之间保留统一水平和垂直间距；
- 新节点不得与已有节点或其他新节点重叠；
- 分组边界包含内部节点和必要留白；
- 更新节点内容时不擅自移动用户已有布局；
- 创建大量镜头时分行排列，避免形成超长单行。

布局完成后用户可以继续手动移动，不影响节点生成配置。

## 11. 手动生成与 Preflight

节点生成按钮和工作流生成按钮继续由用户操作。

系统需要区分两种状态：

- **配置完整**：Route、提示词、参数、引用关系和依赖拓扑合法；
- **立即可生成**：配置完整，并且当前节点需要的上游产物已经存在。

Agent 负责让相关节点达到“配置完整”。用户启动整个工作流时，上游节点可以尚未生成，由 Workflow Run 按依赖顺序完成；用户单独启动下游节点时，生成按钮应等待它所需的上游产物。

用户点击节点或工作流生成时，现有 Canvas Studio Service 执行最终 preflight：

- Route 仍然启用；
- Provider 凭据可用；
- 提示词存在；
- 参数合法；
- 必需素材已经连接；
- 上游生成结果可用；
- 引用没有过期或被删除；
- 没有活动的重复运行。

Agent 在配置阶段应复用同一套 Route、参数、引用和拓扑校验规则，确保“Agent 说配置完成”具有确定含义。运行时素材是否已经产出属于执行就绪检查，不能混入配置完整性判断。前端不能复制另一套近似规则。

如果用户手动修改节点导致配置失效，节点生成按钮应说明具体原因；用户也可以让 Agent 重新检查并修复配置。

## 12. 自动生成设置的处理

当前 UI 和持久化合同中的 `allowAgentGeneration` 不再代表产品当前能力。

推荐分两步处理：

1. 近期从 Agent 面板隐藏“允许自动触发生成”开关，并从 Agent 工具列表移除或永久禁用生成工具；
2. 暂时保留数据库字段和 HTTP 合同以兼容已有项目，读取时不授予 Agent 生成权限；后续稳定迁移中再删除废弃字段。

这样可以避免为了删除一个字段立即扩大数据库和 API 迁移范围，也能确保旧项目即使保存了 `true`，Agent 仍不会触发生成。

## 13. Skills 的边界

短剧 Skill 只负责帮助 Agent 更好地规划和填写画布，例如：

- 剧情冲突、人物关系和节奏；
- 分镜目的、表演、对白密度和竖屏构图；
- 角色、服装、场景和道具连续性；
- 常见镜头的提示词检查清单。

Skill 不固定 Route ID、模型参数、节点数量和完整执行流程。最终 Route 仍从项目当前启用的 Catalog 中选择，参数仍必须通过 Schema 校验，是否创建完整画布仍由本轮用户意图决定。

第一阶段只保留一个内置短剧 Skill。其他创作方法等用户真实需要时再添加，用户也可以安装项目 Skill。

## 14. 架构落点

继续复用现有模块：

```text
PipelineAgentConversationService
  → CanvasAgentIntentResolver
  → CanvasContextAssembler
  → PipelineAgentToolProvider
  → CanvasAgentPlanService
  → CanvasStudioService
```

需要的最小改动：

- `CanvasAgentIntentResolver`：生成阶段收敛为画布准备，并增加节点范围；
- `CanvasAgentTurnPolicyRegistry`：保存并检查本轮节点范围；
- `PipelineAgentToolProvider`：提供 Route 查询和完整节点配置能力，移除 Agent 生成入口；
- `CanvasAgentPlanService`：允许并校验 `routeId`、`settings`、`promptDocument` 和引用配置；
- `CanvasStudioService`：抽取或复用与手动生成一致的配置 preflight；
- Agent 面板：隐藏自动生成开关，清楚显示“节点已准备，可手动生成”。

不新增新的 orchestration framework、Repository、后台 worker 或数据库事实来源。

依赖方向继续遵守：

```text
domain <- ports <- application <- transport
```

Route 和供应商实现留在 infrastructure；Agent 和前端只能通过项目自己的合同与 application service 使用这些能力。

## 15. 分阶段实现

### 阶段 A：关闭 Agent 生成入口

- 隐藏自动生成开关；
- 禁止 Agent 工具启动生成或工作流；
- 保留用户手动生成入口；
- 更新 Agent 提示词和完成文案。

验收：无论旧项目设置为何，Agent 回合都不会产生 Generation Run。

### 阶段 B：完整节点配置

- 为 Agent 提供当前可用 Route、Schema、描述和标签；
- 扩展 Canvas Plan 的节点配置输入；
- 自动填写 Route、参数、结构化提示词和素材引用；
- 应用前使用真实 Route Schema 校验。

验收：Agent 创建的节点无需用户补填技术字段即可通过静态配置检查；工作流可以按依赖顺序生成这些节点。

### 阶段 C：范围和布局可靠性

- 增加本轮节点范围校验；
- 保证局部请求不修改无关节点；
- 完善不重叠布局和大批量分行布局；
- 保证失败 Plan 不留下部分节点。

验收：只准备第 3 镜时不改变其他镜头，新节点不重叠、不遮挡已有节点。

### 阶段 D：真实体验修正

> 当前进度：已根据“短剧”项目真实对话修正操作 Schema 缺失字段、默认滥用首帧模式、
> Skill 仍引导自动生成，以及素材引用与所选 Route 不兼容却能保存的问题。Plan 现在按
> Route Catalog 声明的素材槽位、语义角色和数量约束执行服务端校验。真实验收进一步发现
> Agent 会先制造一次性关键帧，再把所有镜头改走图生视频；当前规则已禁止这种倒置选择，
> 并要求重复角色和场景使用共享参考与兼容的多模态 Route。Route 查询也改为候选摘要与选中
> Route 详情两步读取；详情仅返回 Agent 完成校验和编排所需的参数合法值、范围、默认值、
> 素材槽位和约束，避免 UI 展示元数据与大型枚举标签拖慢长回合。

- 用短剧项目验证剧本、分镜、角色图、单镜视频和整组画布；
- 记录 Agent 选错 Route、引用错误、提示词冲突和参数缺失；
- 只针对真实问题补充 Route 描述、Plan 校验和短剧 Skill；
- 不提前建设通用评分系统。

验收：用户主要通过对话完成画布搭建，只在确认后点击生成。

#### 2026-09-07 最终验收结果

- “只写剧本”只创建 1 个文本节点；“只拆分镜文本节点”只创建 4 个分镜文本节点。验收中发现
  “创建文本节点”曾被误判为画布阶段，意图分类规则现已明确：存储为文本节点不改变剧本或分镜语义。
- 完整画布由 5 个共享参考图、4 个概念帧和 4 个视频节点组成。18 个节点、31 条引用边均成功落库，
  节点间无重叠；4 个视频时长为 5、6、6、7 秒。
- Agent 回合只完成 Route 选择、提示词、参数、引用、布局和预检，没有创建 Generation Run。
- 用户手动触发后，5 个共享参考图和 4 个概念帧全部生成成功；图生图请求分别自动上传 4、5、7、6
  个上游本地制品，无需用户重新选择素材。
- 4 个视频全部生成成功并下载到项目目录。镜头 1、4 使用单一 `firstFrameUrl`，镜头 2、3 使用普通
  多模态 `imageUrls`，所有镜头均未设置 `lastFrameUrl`；远端任务没有重复提交。
- 13 个生成节点最终均为 `succeeded/SUCCESS`，13 个媒体制品均存在于本地；未出现 1013 下载超时、
  生成失败与下载失败混淆，或“运行中”与 Run ID 写入时序导致的重复执行保护误判。

## 16. MVP 验收场景

1. 用户说“写一个短剧剧本”，Agent 只完成剧本文本。
2. 用户说“把剧本拆成 6 个分镜”，Agent 只完成分镜内容。
3. 用户说“把这 6 个分镜搭到画布”，Agent 创建完整节点并停在待生成状态。
4. Agent 为每个生成节点选择兼容 Route、填写合法参数和完整提示词。
5. 角色、服装、场景和道具参考被自动连接到需要它们的节点。
6. 只有明确要求 A 到 B 转场的镜头使用首尾帧。
7. Agent 创建的节点不与现有节点重叠，分组和依赖方向清楚。
8. 用户只要求调整第 3 镜时，其他镜头配置不变化。
9. 用户说“生成第 3 镜”时，Agent 完成第 3 镜配置并提示用户手动生成，不创建 Run。
10. 用户点击生成后，节点通过同一套 preflight 并进入现有持久化运行链路。
11. 缺少兼容 Route 或必要素材时，Agent明确说明缺失项，不创建表面完整但无法运行的节点。
12. 用户手动修改节点后，可以让 Agent 重新检查并修复配置。

## 17. 当前阶段不做

- Agent 自动提交付费生成；
- Route 质量评分和复杂权重；
- 根据历史成功率自动学习；
- 独立的 `ShotProductionSpec`；
- 独立的 `CanvasProductionPlan`；
- 自动生成、评审、重试直到满意的循环；
- 自动 Route 回退和费用预算系统；
- 新增大量内置 Skills；
- 让用户逐节点确认 Agent 的每个技术选择。

以上能力只有在 MVP 的真实使用表明有明确需求时再设计。近期开发的判断标准只有一个：Agent 是否能根据用户本轮意图，把相关画布一次准备到正确、清楚、可手动生成的状态。
