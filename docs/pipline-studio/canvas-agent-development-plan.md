# Pipeline Studio Canvas Agent 开发计划

> 日期：2026-09-03
> 依据：[Canvas Agent 产品调研与技术方案](./canvas-agent-product-research-and-technical-design.md)
> 方法：按可独立体验的纵向切片开发，每个迭代完成后使用真实项目验证并调整下一阶段

## 1. 总体目标

最终交付一个与 Pipeline 项目一对一关联的 Canvas Agent：

- 支持独立、持久的多轮对话和可切换模型。
- 每轮准确识别用户要求的交付范围，不自动扩大到后续生产阶段。
- 理解当前项目、画布、选区、引用、素材和生成状态。
- 能动态规划并创建、修改、连接和整理画布节点。
- 通过项目级开关控制是否允许 Agent 自动触发生成。
- 用户始终可以手动修改节点、手动生成、撤销 Agent 修改并继续对话。

开发过程不一次性完成全部基础设施。每个迭代都要形成用户能看到、能操作、能反馈的闭环。

## 2. 开发顺序总览

| 迭代 | 可体验结果 | 主要风险 | 建议优先级 |
| --- | --- | --- | --- |
| 0. 合同与基线 | 核心状态和边界有明确合同 | 后续反复改数据结构 | 必须先做 |
| 1. 项目独立对话 | 每个项目拥有可恢复的右侧 Agent 面板 | 会话关联和前端边界 | P0 |
| 2. 理解当前画布 | Agent 能回答选中节点和工作流问题 | 上下文过大或读取错误 | P0 |
| 3. 意图与范围控制 | 写剧本就停在剧本，不越界生成 | 模型越权和固定流程倾向 | P0 |
| 4. 自动搭建画布 | Agent 能创建节点、提示词、引用和布局 | 半完成状态、冲突和撤销 | P0 |
| 5. 素材分析与连续性 | Agent 能理解图片、视频、音频并用于规划 | 多模态成本和上下文膨胀 | P1 |
| 6. 自动生成 | 开关允许时按用户意图运行生成 | 误触发、重复执行和长任务恢复 | P0 |
| 7. 结果评审与质量收敛 | 能局部重做、诊断问题并稳定通过真实任务 | 主观质量难评估 | P1 |
| 8. Skills 与高级自动化 | 成功方法可复用，支持受控批量生产 | 过早抽象 | P2 |

迭代 0 至 4 构成第一个可用 MVP；迭代 6 完成用户所需的 Agent 主闭环。迭代 5 可以和迭代 6 的后半段交错推进，但图片分析应早于复杂视频生成场景。

## 3. 迭代 0：合同与基线

### 目标

先固定 Agent 的项目作用域、意图、计划和生成权限边界，避免 UI、工具和数据库各自定义一套状态。

### 工作项

1. 定义共享合同：
   - `PipelineAgentConversation`
   - `PipelineAgentSettings`
   - `CanvasAgentTurnContext`
   - `CanvasAgentTurnIntent`
   - `CanvasAgentPlan`
   - `CanvasAgentOperation`
   - `CanvasAgentAction`
2. 明确状态所有权：
   - 项目与 conversation 关联由服务端持久化。
   - 当前选区和 `@` 引用由每轮请求携带，服务端重新校验。
   - brief、连续性设定和 plan 是结构化项目数据。
   - Generation Run 保持独立 durable 状态。
3. 确定第一版 operation 集合：
   - 创建或更新文本节点。
   - 创建图片、视频和音频生成节点。
   - 创建、更新和删除引用边。
   - 分组、命名和布局。
4. 明确权限公式：

```text
turnIntent.allowedStages 包含 generate
AND projectAgentSettings.allowAgentGeneration = true
AND generation preflight 通过
```

5. 记录现有 `npm run check` 和 `npm run build` 基线，区分已有问题与后续回归。

### 验收

- 合同使用 discriminated union，没有 `any` 或由 UI 猜测的状态。
- 项目 ID 不出现在模型需要自行填写的工具参数中。
- “只写剧本”“搭建但不生成”“完整生成”三个例子的允许动作有明确判定。

## 4. 迭代 1：项目独立对话与右侧面板

### 用户可见结果

打开任意 Pipeline 项目后，右侧有可收起的 Agent 面板。用户可以持续对话，刷新页面或重新打开项目后记录仍然存在；不同项目不会看到彼此的聊天。

### 后端

1. 增加项目与 Agent conversation 的持久绑定：
   - `project_id` 唯一。
   - 保存 Pi session ID、provider、model ID、thinking level、`allowAgentGeneration` 和时间戳。
2. 将现有 `createPipelineAgentSession(projectId)` 改为“读取或创建关联 conversation”。
3. 增加读取和修改项目 Agent 设置的 application use case 与 HTTP 合同。
4. 创建 runtime 时注入服务端绑定的 `pipelineProjectId`，不从模型输入读取项目 ID。
5. 更新 `docs/agent-api-reference.md`。

### 前端

1. 在 `src/features/pipeline-studio` 内增加：
   - `agent-panel/agent-panel.tsx`
   - `agent-panel/agent-composer.tsx`
   - `agent-panel/agent-message-list.tsx`
   - `agent-panel/use-pipeline-agent-controller.ts`
2. 面板固定停靠右侧：
   - 顶部：收起、运行状态、模型选择器、自动生成开关。
   - 中部：消息和工具动作。
   - 底部：固定输入框和发送/停止操作。
3. 面板宽度、收起状态按项目恢复。
4. 不允许 `pipeline-studio` 直接导入 `features/chat`。确实通用的无业务展示能力再提取到 `src/components/ui`，其余逻辑保留在 Pipeline Studio 内。
5. 更新中英文词典。

### 测试与验证

- Repository：一项目一 conversation、不同项目隔离、设置持久化。
- Application：重复打开返回同一 conversation，模型切换从下一轮生效。
- Transport：项目不存在、模型不可用、非法设置输入。
- UI：面板收起、恢复、底部输入、模型与开关状态。
- 浏览器：在两个项目间切换，确认消息和设置互不串联。

### 本阶段暂不做

Agent 可以正常聊天，但尚不声称理解画布，也不能修改画布或触发生成。

## 5. 迭代 2：实时画布上下文

### 用户可见结果

用户选中节点后询问“这些节点是什么关系”“为什么这个视频节点不能运行”，Agent 能根据当前真实画布回答。

### 后端

1. 实现 `CanvasAgentContextAssembler`：
   - 项目摘要和当前 revision。
   - 显式 `@` 引用。
   - 当前选中节点。
   - 选区相邻的上游引用和下游派生节点。
   - 节点 Route、参数、任务状态和 generation provenance。
2. 每轮请求接受最小的上下文指针：
   - `canvasRevision`
   - `selectedNodeIds`
   - `mentionedReferences`
3. 服务端重新读取并验证所有 ID，客户端不能直接提交节点正文作为可信事实。
4. 新增只读工具：
   - `canvas_get_context`
   - `canvas_get_capabilities`
   - `canvas_get_run_status`
5. 设置上下文预算和渐进读取策略，默认不发送完整画布。

### 前端

1. 选中节点自动显示在 composer 上方，可逐个移除。
2. 支持 `@` 搜索节点、资产、分组和生成历史。
3. 消息中展示本轮使用了哪些画布对象。
4. 画布变化后，下一轮自动使用新 revision，不复用旧快照。

### 测试与验证

- 上下游子图选择正确。
- 已删除或跨项目 ID 被拒绝。
- 大画布只返回相关子图，内容有稳定上限。
- 用户手动修改节点后，Agent 下一轮能读取新内容。
- 两个项目使用相同节点名称时不会串上下文。

## 6. 迭代 3：意图识别与范围控制

### 用户可见结果

Agent 能根据不同要求停在正确阶段：讨论创意不改画布，写剧本不拆分镜，搭建工作流但不生成时只准备节点。

### 后端

1. 实现 `CanvasAgentIntentResolver`，为每轮生成结构化 `CanvasAgentTurnIntent`。
2. 将 intent 注入 planner 和工具执行上下文。
3. 在 application 层实现 `allowedStages` guard，不能只依靠 system prompt。
4. 定义覆盖规则：
   - 最新明确要求覆盖旧假设。
   - “不要生成”覆盖项目自动生成开关。
   - 建议下一步不产生新的执行权限。
5. 对模糊需求只提出会改变当前交付的少量问题。
6. 保存已确认的项目事实，但不把临时讨论自动写入 continuity bible。

### 第一批评估用例

| 输入 | 期望停止位置 |
| --- | --- |
| “帮我想三个方向” | 对话建议 |
| “写一个 30 秒香水广告剧本” | 剧本文本 |
| “把这个剧本拆成 6 个镜头” | 分镜计划 |
| “节点和提示词准备好，我自己生成” | 可运行画布节点 |
| “做成完整视频”且自动生成关闭 | 可运行节点，不创建 Run |
| “做成完整视频”且自动生成开启 | 可以创建 Run |

### 测试与验证

- 结构化 intent schema 稳定。
- 生成工具在 `allowedStages` 不包含 `generate` 时被服务端拒绝。
- 多轮修改范围有效，例如先要求完整视频，随后说“先只把剧本改好”。
- 统计并检查范围越界率。

## 7. 迭代 4：计划与画布操作

### 用户可见结果

用户可以说“把这个剧本拆成三个镜头并把节点搭好”，Agent 会在画布上创建、连接和整理出可编辑的子图，但不会触发生成。

### Domain 与 Application

1. 实现 `CanvasAgentPlanService`：
   - 创建计划。
   - 根据反馈局部更新计划。
   - 持久化计划摘要、base revision、operations 和状态。
2. 实现 `CanvasAgentPlanValidator`：
   - 项目归属。
   - intent 范围。
   - 节点类型与引用角色。
   - Route 输入要求。
   - 节点数量与拓扑限制。
3. 实现 `CanvasAgentPlanResolver`：
   - 临时引用映射为稳定 ID。
   - 选择节点尺寸和布局。
   - 把语义 operation 展开为 `CanvasMutation[]`。
4. 实现 `CanvasAgentPlanExecutor`：
   - 单次 `CanvasMutationBatch` 原子提交。
   - revision 冲突检测和无冲突 rebase。
   - 写入 `CanvasAgentAction`。
   - 生成可撤销数据。
5. 新增工具：
   - `canvas_create_plan`
   - `canvas_apply_plan`
   - `canvas_update_plan`
   - `canvas_undo_action`

### 前端

1. 对话中显示紧凑计划摘要和关键假设。
2. Agent 操作画布时显示阶段状态。
3. 应用后定位到新子图，并提供一次性“撤销本次修改”。
4. Agent 创建的节点与手动节点使用相同组件和编辑能力。
5. 用户修改 Agent 节点后，后续计划把它视为普通用户内容，不擅自覆盖。

### 测试与验证

- 三镜头计划形成正确节点、引用角色和布局。
- 计划应用失败时不留下半套节点。
- 重复 tool call 不重复创建节点。
- revision 冲突不会覆盖用户刚做的修改。
- 应用再撤销后画布回到等价状态。
- 刷新后计划和 Agent action 可恢复。

### MVP 检查点

到这里先进行一次真实体验评审。至少完成：

1. 空画布生成广告剧本和三镜头结构。
2. 从已有文本节点增量创建分镜。
3. 用户手动修改其中一个镜头后，让 Agent 只调整剩余节点。
4. 关闭面板、刷新页面、重新打开后继续对话。

如果此时 Agent 仍经常越界、创建错误引用或难以局部修改，应先修正计划模型，不进入自动生成阶段。

## 8. 迭代 5：素材分析与连续性

> 当前进度：已完成图片结构化分析与按素材指纹/模型复用、项目连续性版本化持久化、用户确认原文校验、视频有界帧采样与镜头摘要，以及音频节奏、动态和静音分析。语音转写与基于音频语义的情绪摘要需要新增语音模型端口，留在本迭代后续批次。

### 用户可见结果

用户把图片、视频或音频放入画布并与 Agent 交流，Agent 能解释素材内容、建议引用角色，并把已确认的主体和风格用于后续镜头。

### 实施顺序

1. 图片分析：
   - 主体、构图、材质、风格、光线、文字和品牌元素。
   - 适合作为主体、场景、风格、首帧、尾帧还是反例。
2. 连续性设定：
   - 角色、产品、场景、服装、色彩和镜头语言。
   - 用户修正后结构化持久化。
3. 视频分析：
   - 使用媒体元数据和采样关键帧。
   - 镜头切分和运动摘要。
4. 音频分析：
   - 元数据、转写、节奏和情绪摘要。

### 技术工作

- 新增 `canvas_inspect_assets` 工具。
- 分析任务与 Agent 对话解耦，结果持久化并可复用。
- 视频和音频先由确定性预处理器生成紧凑输入，再调用多模态模型。
- 分析结果记录来源、模型、时间和用户修正，不把模型判断直接当作不可变事实。
- 素材文件读取继续限制在注册项目根和受控 artifact 范围内。

### 测试与验证

- 图片分析可以生成引用建议，用户修改后不会被旧结果覆盖。
- 同一素材重复分析可以复用结果或明确创建新版。
- 不支持视觉输入的 Agent 模型给出具体禁用原因。
- 大视频不会被整体放入聊天上下文。

## 9. 迭代 6：自动生成权限与执行

### 用户可见结果

自动生成关闭时，Agent 把节点准备好并停下；开启后，用户明确要求生成完整内容时，Agent 可以主动执行并管理运行。

### 后端

1. 实现 `canvas_prepare_generation`：
   - 解析实际节点和依赖。
   - 运行 Route Schema 与 workflow preflight。
   - 生成确定的 prompt、参数和 asset bindings。
2. 实现 `canvas_run_generation`：
   - 强制检查 project-bound session。
   - 强制检查本轮 intent。
   - 强制检查 `allowAgentGeneration`。
   - 使用稳定 idempotency key 创建 Generation Run。
3. 复用现有 durable Generation Run 和 worker，不在 Agent tool loop 内承担长任务可靠性。
4. 支持 DAG 顺序、受控并发、取消、失败重试和从失败节点继续。
5. 防止通过“运行工作流”一类间接工具绕过自动生成开关。
6. 开关变化立即作用于后续生成调用；已经创建的 Run 按现有取消规则处理。

### 前端

1. 开关关闭：Agent 消息提示节点已经准备完成，用户可在节点上手动生成。
2. 开关开启：Agent 展示即将运行的节点、Route 和数量，然后在当前意图允许时开始运行。
3. 对话动作与画布节点展示同一 `runId` 状态。
4. 收起面板或刷新页面后继续显示真实运行状态。

### 测试与验证

- 开关关闭时所有 Agent 调用路径都无法创建 Run。
- 手动节点生成在开关关闭时仍然可用。
- 开关开启但用户只要求剧本时不会创建 Run。
- 重复消息、重连和重试不会产生重复付费任务。
- 进程重启后 Run、plan 和对话关联可以恢复。
- 上游内容变化后只提示或重跑过期下游节点。

## 10. 迭代 7：结果评审与质量收敛

### 用户可见结果

Agent 能比较多个 take、解释明显问题，并根据“第二镜头太快”“人物不一致”等反馈只修改受影响部分。

### 工作项

- 为图片和视频结果建立紧凑评审输入。
- 根据 shot spec 检查主体、构图、动作、镜头、风格和连续性。
- 结果建议与最终选择分离，Agent 不擅自锁定主观最佳结果。
- 建立上游变化到下游受影响范围的计算。
- 支持替换 Route、调整提示词和局部重跑。
- 将成功子图保存为普通 workflow。

### 真实回归项目

1. 15 秒产品广告：单产品图、三镜头、风格连续。
2. 固定角色短片：角色参考、场景变化、四至六镜头。
3. 长脚本分镜：只生成脚本和 shot plan，不自动运行媒体生成。

每次重要改动都运行这三套任务，记录：完成时间、手动节点操作数、越界执行、Undo 次数、无效生成和局部重跑成功率。

## 11. 迭代 8：Skills 与高级能力

只有核心闭环稳定后再进入：

- 广告、短剧、MV、口播和产品展示 Skills。
- 从成功计划提炼可复用模板。
- 项目级 Route 和风格偏好。
- 自动诊断断线、过期结果和不可运行节点。
- 有上限的批量变体和方向探索。
- 可选预算、最大节点数和最大并发数。

暂不引入多 Agent。导演、编剧和分镜等职责先作为同一个 planner 内部的结构化步骤，等单 Agent 的质量和可观察性稳定后再判断是否需要拆分。

## 12. 建议的提交与评审粒度

每个迭代拆成多个可独立审查的提交或 PR，避免一次修改 Agent、画布、生成和 UI 全部链路。

推荐顺序：

1. Contracts 与数据库绑定。
2. Application use case 与项目作用域测试。
3. HTTP API 和文档。
4. Pipeline Studio controller/state。
5. 右侧面板 UI 和 i18n。
6. 对应工具与执行器。
7. 浏览器验证和回归修复。

复杂实现开始前按项目规则创建普通 `feature/*` 分支。当前工作区已有未提交的 `studio-canvas.tsx` 修改，切换分支前必须先保留该修改，不能覆盖或带入无关提交。

## 13. 每个迭代的完成标准

一个迭代只有同时满足以下条件才算完成：

- 用户可见行为达到本阶段验收场景。
- 新增非平凡分支具有 focused tests。
- 不同项目的数据隔离有服务端测试。
- UI 新文案同时更新中英文词典。
- 公共 HTTP 合同变化同步到 `docs/agent-api-reference.md`。
- 没有从 UI 导入 `src/server`，也没有跨 feature 直接依赖。
- 生成、取消、SSE、刷新恢复和错误状态没有退化。
- 运行一次 `npm run check`。
- 涉及 Next.js 路由、渲染、配置或生产行为时运行 `npm run build`。
- 交互阶段在浏览器验证 1024、1440 和 1920 宽度、键盘焦点、面板收起和暗色对比度。

## 14. 建议从哪里开始

第一个开发迭代建议只完成以下闭环：

```text
打开 Pipeline 项目
-> 自动读取或创建该项目的 Agent conversation
-> 右侧面板恢复聊天
-> 可切换 Agent 模型
```
